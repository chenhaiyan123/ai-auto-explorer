# Problem Heartbeat 现状核查

> 以下为实施前审计。三项补充已在后续版本完成代码与测试，见 [发布说明](问题心跳与英文设置-发布说明.md)。云端接入状态以发布说明为准。

2026-09-10。核查对象为当前本地代码中的问题唤醒后台、项目生命面板和既有浏览器通知流程。本文是检查结果和后续建议，不表示这些建议已经实现或上线。本次未修改产品行为。

## 结论

已有按需运行 AI 的基础执行机制，还没有完整实现何时值得让问题重新进入用户注意力的产品机制。当前 `heartbeatAt` 是执行器存活信号，不是用户提出的 Problem Heartbeat。问题等待、认知变化、注意力管理应单独持久化。

## 已实现的基础

- 用户材料、首次上下文同步、事实或目标变化、论文元数据、周期复盘可以进入持久事件队列。新问题必须先同步并开启后台研究，不能把这个能力表述为创建即自动完成四个假设。
- 没有待处理线索且未到复盘时间时，不调用模型。默认每天检查；连续无采集更新退避至三倍间隔；默认每七天复盘，可配置。
- 一轮先由经理决定 research 或 wait。wait 只调用一次；研究通常为经理、思想家或执行者、验证者、审计者四次调用。受预算限制，出错停止、不自动重试。
- 事件按 ID 去重；已采纳候选的陈述去空白、转小写后做完全重复过滤。没有实现语义去重和同源转载关联。
- 研究保存触发原因、步骤、摘要、下一步、材料引用及事实快照；确认事实的新增、撤回和修改有差异记录。候选不会自动成为已确认事实。
- 状态灯依赖新鲜的执行器心跳；关闭页面继续工作的后台代码存在，但正式云端部署和关电脑实测仍未完成。

## 对照五类唤醒

| 类别 | 当前情况 | 缺口 |
| --- | --- | --- |
| World Changed：世界变化、机会、风险 | 有 Crossref 元数据检索和用户材料输入 | 没有通用来源订阅、版本游标、条件阈值、机会与风险优先级；Crossref 按相关性取前 20 项，可能遗漏新发表的相关论文 |
| Knowledge Changed：证据、矛盾、认知跃迁 | 事实变化可触发通用事件，有事实快照与增删改记录 | 没有稳定的判断版本、支持/反对关系及冲突优先路由；事实变化不能自动等同于认知跃迁 |
| Action Needed：数据、实验、决策、权限 | 经理可以在文本里写下一步；旧浏览器流程已有部分决策/现实验证提示 | 新唤醒引擎没有结构化待办、授权请求和用户答复恢复机制；`needs_user` 只定义了名称，没有进入该状态的运行路径 |
| Problem Changed：停滞、新分支、解决、失效 | 有既有探索树，可手动保存或分叉 | 没有长期无实质进展检测、分支出生提案或问题完成/失效状态与唤醒计划的关联 |
| Human Changed：兴趣、目标、优先级 | 修改同步上下文可触发通用事件 | 没有定期关心程度确认、兴趣衰减策略、免打扰或用户目标变化的独立记录 |

## 关键差距与证据

### 1. 研究唤醒与用户提醒尚未分开

`wakeRunner.ts` 的经理只输出 research / wait，没有 shouldNotify、注意力优先级、通知理由、静默合并或用户阅读游标。`ProjectLifePanel.tsx` 展示最近十轮，包括等待轮次，不是“自上次访问以来的重要变化”。

现有 `App.tsx` 有浏览器内发现、决策、实验等通知，保存在 React state，最多二十条；未与云端唤醒结果形成持久通知链路。已有移动推送注册辅助代码，也不等于已接入长期研究的通知投递。不能宣称用户离开一个月后会被主动找回。

### 2. 等待条件没有成为可执行规则

经理的 `stopCondition` 只校验是非空字符串；审计的 `next` 也是文本。运行完成统一回到 sleeping。系统没有保存“等哪份数据、由谁提供、什么阈值满足后恢复、影响哪个假设”的结构。

`needs_user` 在 `awakening.ts` 有定义，但唤醒运行器没有给它赋值。等待用户输入、外部观察、长期休眠和用户主动暂停尚未完整区分。

### 3. 计划增量可能被标记为研究进展

当前 `progress` 判定为：审计返回 progress，且存在没有完全重复的候选条目。候选允许无证据的 plan / hypothesis。这对记录规划工作可以成立，但不足以表示“判断因证据改变”，更不能直接触发“突破”通知。

不能只靠模型声称重要或给出新措辞；需要记录旧判断、新判断、依据、适用范围以及什么仍未验证。没有新证据时，允许有价值的方法复盘，但应与证据进展分别展示。

### 4. 缺少持久问题生命周期

当前主要状态为 sleeping / checking / researching / needs_user / blocked / paused。没有 Waiting、Watching、Dormant、Resolved 的产品语义及配套数据，也没有问题沉睡时长、上次实质进展时间和回来后的摘要。

`quietChecks` 统计的是本次采集有没有增加事件，并不代表连续多少天没有认知进展。不能用它直接宣称“过去六天没有值得打扰你的发现”。

## 建议的最小下一版

按三个关口实现，而不是新增十几类弹窗：

1. **观察关口**：持久保存关注来源、等待对象和命中条件。检查、去重和简单阈值判断尽量不调用模型。
2. **研究关口**：事件值得研究且有预算时，运行有限任务。产物分别标为规划、候选证据、核验结果和判断变化。重要原始材料可以先触发核验，不必先通知用户，也不能先当成可信事实。
3. **注意力关口**：独立决定静默记录、下次访问展示、合并摘要或立即请求用户。保存已读位置、发送记录、去重键、冷却时间和通知理由。

先完成以下三件事：

- **结构化等待与需要你**：等待什么、来源/负责人、触发条件、下次检查时间；决策请求保存所需资源、授权范围与待答状态。收到答复或数据只恢复受影响的任务。
- **认知变化记录与回访摘要**：旧判断 → 新判断 → 支持/反对证据 → 影响的决定 → 下一步。无变化的检查合并，规划工作不冒充现实发现。
- **长期状态和通知门槛**：停滞复盘、休眠、重新激活、兴趣变化；先实现站内持久待办与摘要，再接用户选择的外部通知渠道。

不建议把所有状态串成必须依次经过的九步：等待实验时也可能持续观察论文，探索中也可能需要人审批。问题生命周期、执行器运行状态、是否需要用户注意应分别记录；首页再将这些组合成易懂的状态标签。

“重要性 × 新颖度 × 可信度 × 可行动性”可作解释框架，不应直接作为唯一硬门槛。可行动性低的重要结论仍可能值得知晓；可信度不足可能正是需要人补材料的原因。风险和授权请求应走单独规则，带不确定性说明；其余提醒再考虑评分、去重和用户偏好。模型自评分不能代替来源核验。

## 验证结果及下一版验收场景

本次重新运行当前 `__test__/awakening.test.ts`：15 项全部通过，使用模拟响应，不产生真实模型费用。涵盖无材料零调用、四角色流程、去重、预算、暂停、伪造引用、事实撤回、重启和 30 天时间推进。

现有“30 天无新增证据”用例产生四次复盘、十六次模型调用、一次规划性 progress；这验证有界运行，不代表真实研究取得进展。没有实际等待三十天或运行真实实验。

下一版还应新增行为验收：

- 等用户销售数据期间，重复输入不会重复提醒或重复运行；数据到达后只恢复相关任务。
- 新论文只记录相关线索，不自动广播突破；出现经核验的矛盾后才生成判断变更卡。
- 连续三十天无有效增量，诚实提示一次停滞与等待方案，进入适当休眠，用户主动暂停不能被定时器解除。
- 高影响但暂时无法行动的证据，不因乘积得零被静默丢弃。
- 需要三千元实验投入时，保存待授权请求；未获授权不得执行，重复或过期授权不能再次启动。
- 用户一个月后回来，只看到上次阅读之后的相关变化和待办，检查日志不会淹没实质进展。
