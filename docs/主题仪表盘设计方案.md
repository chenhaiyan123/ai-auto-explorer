# 主题化项目仪表盘 · 设计方案

> 目标：每个项目的「总览」顶部有一块**贴合该项目主题**的仪表盘，由该项目的 AI 管家生成，用户可以在管家对话里用自然语言调整它。
> 用户打开总览，5 秒内看懂：**做什么 / 什么阶段 / 下一步 / 卡在哪 / 拿到了什么**。

技术路线（已确认）：**配置驱动** + **节点计算 + AI 叙述**。
AI 管家不写代码、不算数字——它只产出一份 JSON 配置和一段结构化叙述；数字全部由现有纯函数从节点实时算出。

---

## 一、现状盘点

| 已有 | 位置 | 状态 |
|---|---|---|
| 通用仪表盘计算 | `services/dashboardService.ts` → `buildDashboard()` | 纯函数、无副作用，可直接复用 |
| 通用仪表盘 UI | `components/ProjectDashboard.tsx` | 五个写死板块：简介/异常/方向/团队/成果 |
| 挂载点 | `components/NodeDetails.tsx:522`（仅 `noteType === 'overview'` 的笔记） | 不动 |
| AI 管家 | `App.tsx` `AIButler`（L55 起），已有 `[ACTION:ADD_NODE:x]` 指令解析（L~285） | 复用其指令通道 |
| 总览正文自动合成 | `App.tsx` `refreshOverview()`（L1306），`autoNote===false` 时不覆盖 | 复用其节流与上下文 |

**核心问题**：仪表盘是"一套模板打天下"。做硬件研发的项目和写论文的项目，看到的是同一组板块、同一套口径。

## 二、数据模型

在 `types.ts` 的 `Project` 上新增两个可选字段，**老项目不迁移、缺省即降级为当前通用仪表盘**。

```ts
export interface Project {
  // ...existing
  /** AI 管家生成的仪表盘配置（慢变，用户可对话调整） */
  dashboardSpec?: DashboardSpec;
  /** AI 管家定期总结的叙述性判断（快变，随探索刷新） */
  dashboardNarrative?: DashboardNarrative;
}
```

### 2.1 DashboardSpec —— 「长什么样、看什么口径」

```ts
export interface DashboardSpec {
  version: 1;
  /** AI 判断的项目类型，用于挑默认模板与措辞，如「硬件研发」「学术研究」「内容创作」 */
  theme: string;
  /** 一句话定位：它是做什么的 */
  headline: string;
  /** 主题化的阶段模型，如 立项→选型→打样→测试→量产 */
  stages: StageDef[];
  /** 顶部关键指标（口径由 spec 决定，最多 4 个） */
  metrics: MetricDef[];
  /** 板块顺序 / 开关 / 措辞 */
  blocks: BlockDef[];
  updatedAt: number;
  /** 'ai' = 管家生成；'user' = 用户手动或对话改过，AI 不再整份覆盖（对齐 autoNote 的思路） */
  updatedBy: 'ai' | 'user';
}

export interface StageDef {
  id: string;
  label: string;        // 「打样验证」
  hint?: string;        // 「做出第一版能跑的样机」——鼠标悬停说明
}

export type MetricSource =
  | 'progress'        // 整体/筛选后进度，取 nodeScore 加权
  | 'count_nodes'     // 满足 filter 的方向数
  | 'count_results'   // 成果条数（agentResults + manualResults）
  | 'count_notes'     // 笔记篇数
  | 'count_alerts'    // 异常数
  | 'count_agents'    // 参与 Agent 数
  | 'narrative';      // 取 narrative.customMetrics[id]，由 AI 填文本

export interface MetricDef {
  id: string;
  label: string;                     // 「样机迭代轮次」
  source: MetricSource;              // ★ 白名单，AI 只能选不能自由发挥
  filter?: {                         // 口径收窄，全部可选
    status?: NodeStatus[];
    area?: string;                   // 匹配 node.folder
    tag?: string;                    // 匹配 node.tags
    titleMatch?: string;             // 正则字符串，运行时 try/catch 编译
  };
  format: 'percent' | 'number' | 'ratio' | 'text';
  goal?: number;                     // 有目标值时渲染成环形进度
  emphasis?: 'hero' | 'normal';      // hero = 左侧大字位
}

export type BlockKind =
  | 'intro'        // 是做什么的
  | 'stage'        // 现在什么阶段
  | 'metrics'      // 关键指标条
  | 'plan'         // 下一步计划
  | 'alerts'       // 遇到什么问题
  | 'achievements' // 关键成果
  | 'directions'   // 主攻方向卡片
  | 'team';        // 团队分工

export interface BlockDef {
  kind: BlockKind;
  title: string;      // AI 按主题改措辞：研究项目叫「待验证的疑点」，创业项目叫「当前风险」
  visible: boolean;
  options?: Record<string, string | number | boolean>;  // 如 { limit: 5, onlyActive: true }
}
```

**为什么用「白名单 source + filter」而不是让 AI 写表达式**：可静态校验、可安全降级、模型跑偏时最多是指标没意义，不会白屏。

### 2.2 DashboardNarrative —— 「AI 的判断」

节点算不出来的东西才放这里，每项都带 `evidenceNodeIds` 以便一次点击溯源。

```ts
export interface DashboardNarrative {
  /** 当前处于 spec.stages 里的哪一阶段 */
  currentStageId: string;
  /** 为什么判定在这个阶段（一句话） */
  stageReason: string;
  /** 下一步计划：3–5 条，动词开头 */
  nextSteps: { text: string; horizon: 'near' | 'mid'; nodeId?: string }[];
  /** 实质卡点（区别于规则算出的「停滞/无人负责」这类形式异常） */
  blockers: { text: string; impact?: string; nodeId?: string }[];
  /** 管家挑出的高光成果（从 achievements 里选，不新造） */
  highlights: { nodeId: string; text: string }[];
  /** source==='narrative' 的指标取值 */
  customMetrics?: Record<string, string>;
  updatedAt: number;
}
```

## 三、五个问题 → 板块 → 数据来源

| 用户的问题 | 板块 | 数字/事实来自 | 判断来自 |
|---|---|---|---|
| 它是做什么的？ | `intro` | `extractIntro(overview)` 兜底 | `spec.headline` |
| 现在什么阶段？ | `stage` | 各阶段完成度按 `nodeScore` 算 | `narrative.currentStageId` + `stageReason` |
| 进一步计划？ | `plan` | 待探索节点、无人负责的方向 | `narrative.nextSteps` |
| 遇到什么问题？ | `alerts` | `buildDashboard().alerts`（停滞/待复核/无人负责/空白） | `narrative.blockers` |
| 关键成果？ | `achievements` | `buildDashboard().achievements` | `narrative.highlights` 置顶 |

原则：**AI 负责措辞与判断，规则负责数字与链接**。AI 服务不可用时，去掉 narrative 仍是一个可用的仪表盘。

## 四、计算层改造

`services/dashboardService.ts` 保持纯函数，追加：

```ts
/** 解析单个指标 → 展示值（不含措辞） */
export function resolveMetric(def: MetricDef, nodes: ProblemNode[], now?: number): {
  value: number | string; display: string; nodeIds: string[];
}

/** 各阶段完成度：把方向按 folder / 标题关键词归到 stages，再取 nodeScore 均值 */
export function stageProgress(spec: DashboardSpec, nodes: ProblemNode[]): { id: string; progress: number }[]

/** 主入口签名扩展（spec/narrative 可选，不传即当前行为，向后兼容） */
export function buildDashboard(
  nodes: ProblemNode[], now?: number,
  spec?: DashboardSpec, narrative?: DashboardNarrative
): DashboardData
```

`DashboardData` 新增 `spec`、`narrative`、`metrics: ResolvedMetric[]`、`stages: {id,label,progress,current}[]`。现有字段一个都不删——`ProjectDashboard` 的默认渲染路径继续吃老字段。

## 五、AI 管家链路

### 5.1 生成 spec（一次性 / 低频）

- **触发**：① 项目首次开始探索时（挂在 `refreshOverview('start')` 之后）；② 总览页点「🏠 让管家定制仪表盘」；③ `dashboardSpec` 为空时懒生成。
- **输入**：项目名、`metaProblem`、`explorationMode`、README + 总览正文、全部方向标题与 `folder`、已有 Agent 角色。
- **输出**：`DashboardSpec` JSON（复用现有 `callGemini` + "返回纯 JSON，不要 markdown" 的约定）。
- **校验**：手写 `validateSpec(raw): DashboardSpec | null`——枚举白名单校验、非法字段丢弃、`metrics` 截断到 4、`blocks` 去重补全。校验失败 → `DEFAULT_SPEC`（即当前通用五板块），只在控制台告警，不打扰用户。

Prompt 骨架（放 `services/dashboardService.ts` 同级新建 `services/dashboardSpecService.ts`）：

```
你在为一个探索项目设计"总览仪表盘"。先判断这个项目属于哪类工作（研发/研究/创业/内容/学习…），
然后选出该类工作的人真正每天会看的阶段与指标。
- stages：4–6 个，用这个领域的人自己的说法，不要用「阶段一/阶段二」
- metrics：≤4 个，source 只能从给定枚举里选
- blocks：从给定 kind 里选，按重要性排序，title 用贴合领域的措辞
不要编造项目里没有的东西。返回纯 JSON。
```

### 5.2 刷新 narrative（跟随探索）

搭车 `App.tsx` 的 `refreshOverview()`：同一批上下文，让模型在合成总览正文的同时多返回一段 narrative JSON，复用它已有的 `overviewRefreshingRef` 节流与「每解决若干节点刷新一次」的时机。**不新增调用频次。**

### 5.3 对话调整（用户 ↔ 管家）

沿用 `AIButler` 已有的指令通道风格，新增一条：

```
- 如果用户要求调整总览仪表盘（增删板块、改指标口径、改阶段、改措辞），
  在回复末尾加上：[ACTION:DASHBOARD:{JSON Merge Patch}]
  只输出改动的部分，不要重发整份配置。
```

`App.tsx` 解析侧：

```ts
const m = response.match(/\[ACTION:DASHBOARD:([\s\S]+?)\]\s*$/);
if (m) {
  const patch = safeJson(m[1]);
  const next = validateSpec(mergePatch(project.dashboardSpec ?? DEFAULT_SPEC, patch));
  if (next) updateProject({ dashboardSpec: { ...next, updatedAt: Date.now(), updatedBy: 'user' } });
}
```

用 **JSON Merge Patch** 而不是整份重写：避免模型每次重发时悄悄丢掉用户之前的调整。`updatedBy: 'user'` 之后，自动生成不再整份覆盖（只补空缺字段），与 `autoNote` 的处理一致。

典型对话：

> 用户：团队分工那块我不看，把它收起来；加一个"样机轮次"的指标
> 管家：好，已经把团队分工收起来，顶部加了「样机轮次」（按标题含"打样/样机"的方向计数）。`[ACTION:DASHBOARD:{"blocks":[{"kind":"team","visible":false}],"metrics":[{"id":"proto","label":"样机轮次","source":"count_nodes","filter":{"titleMatch":"打样|样机"},"format":"number"}]}]`

## 六、UI 改造（`components/ProjectDashboard.tsx`）

1. 渲染改为 `spec.blocks.filter(b => b.visible).map(renderBlock)`，`renderBlock` 是 `BlockKind → 组件` 的查表；现有五块直接拆成五个函数复用。
2. 顶部加一条极窄的配置行：
   `🏠 管家配置 · 硬件研发　[⚙ 调整]` —— 点「调整」打开管家聊天并预填「帮我调整总览仪表盘：」。
3. 新增三个板块组件：`StageBar`（横向阶段条，当前阶段高亮 + 悬停 hint）、`MetricStrip`（≤4 个指标，hero 一个大字）、`PlanList`（下一步，带 `nodeId` 的可跳转）。
4. `alerts` 板块合并展示：规则异常（现有徽章）在上，`narrative.blockers` 在下并标注「管家判断」，视觉上区分开事实与判断。
5. 未生成 spec 时：渲染 `DEFAULT_SPEC`，并在顶部显示一个「让管家为这个项目定制」的按钮。
6. 板块标题右侧加 `👁` 快捷开关 → 直接写 `spec.blocks[].visible`，`updatedBy='user'`。

## 七、实施顺序

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 | `types.ts` 加类型；`DEFAULT_SPEC`；`ProjectDashboard` 改为 spec 驱动 | 所有老项目视觉零变化 |

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| AI 生成的指标口径无意义（如"样机轮次"永远是 0） | 指标解析后为 0 且 `filter` 命中 0 个节点时，UI 灰显并提示「口径没匹配到内容，可让管家改」 |
| 模型跑偏 / JSON 不合法 | `validateSpec()` 白名单校验 → 失败静默回退 `DEFAULT_SPEC` |
| 用户手调后被自动生成覆盖 | `updatedBy==='user'` 后只补空字段，不整份覆盖（同 `autoNote`） |
| spec 结构后续升级 | `version` 字段 + `migrateSpec(v)`；不认识的版本直接回退默认 |
| `titleMatch` 正则注入/异常 | 编译时 try/catch，失败视为无 filter；长度上限 64 |
| 调用成本 | spec 低频（项目级一次 + 用户主动改）；narrative 搭车已有的总览刷新，不新增调用 |
