## 二、有没有浪费：有，而且是主要成本

### 已排除的浪费项

- **无预留实例**：`hiexplore-auth` 弹性策略为空、函数配额未配置，最小实例数 0。
  所以**不存在零流量也计费的空转实例**，这条最常见的坑你没踩。
- **OSS 几乎为零**：¥0.09/月，不值得动。虽然桶散落在「无地域属性」和「华南1（深圳）」两处，
  但金额是小数点后四位量级，属于历史遗留，清理它的收益接近 0。
- **另两个函数** `aliyun-ai-proxy`、`qwen_API` 最近 24 小时调用 0 次，且无预留实例 → 不产生费用。
  （建议删除，但理由是**减少暴露面**，不是省钱——它们可能还带着旧的 API Key。）

### 真正的浪费：FC 按执行时长计费，而 `/api/chat` 在同步等待大模型

这是关键的成本结构问题：

```
浏览器 → FC /api/chat → DeepSeek（响应通常 5~20 秒）→ 返回
              ↑
        这 5~20 秒，FC 实例一直活着，全程计入 CU
```

FC 收的是 **vCPU·秒 + 内存·秒**，不是请求次数。函数在等待上游 HTTP 响应的整段时间都在计费，
哪怕它什么都没算。所以每一次模型调用的真实成本 = DeepSeek 的 token 费 + FC 的等待时长费。

叠加上前端那个空转循环（见 commit `7c64427`），账单被放大了两次：

1. 后端挂掉/额度用尽时，前端每 500ms 重试一轮、持续模式还每 8 秒造新方向 →
   实测 24 小时 2973 次调用、**全部失败**
2. 每次失败也要走完 FC 的启动 + 等待上游超时，**失败的调用一样计费**

也就是说 2026-07 那 ¥16.11 里，相当一部分是买了「反复失败」。

## 三. 建议动作（按性价比排序）

| # | 动作 | 省多少 | 状态 |
|---|---|---|---|
| 1 | 前端识别链路级故障后立即停循环，不再空转 | 消除失败调用这一整块 | ✅ 已改（`7c64427`），待 push |
| 2 | 开「费用预警」：账户余额 / 月度消费阈值短信提醒 | 不省钱，但不会再欠费停服 | ⬜ 待做 |
| 3 | 把 `TRIAL_GLOBAL_DAILY_CAP` 从 2000 调低（如 300） | 封住单日最大损失 | ⬜ 待定 |
| 4 | 删除 `aliyun-ai-proxy`、`qwen_API` 两个闲置函数 | ¥0（目的是减少 Key 暴露面） | ⬜ 待做 |
| 5 | 长期：`/api/chat` 改流式转发或让前端直连自带模型 | 砍掉 FC 的等待时长 | ⬜ 架构级，可选 |

### 关于第 2 项（最该马上做）

这次欠费导致的后果远大于费用本身：登录后端和体验代理全挂，
40 个访客里可能大部分是**因为登录坏了而流失**的。¥30 的余额断掉，代价是整个产品对外不可用。

设置路径：费用与成本 → 成本监控 → 预算管理，或首页「自动充值设置」。
建议同时设：余额低于 ¥20 提醒 + 月度消费超 ¥30 提醒。

### 关于第 3 项

`TRIAL_GLOBAL_DAILY_CAP=2000` 的含义是：最坏情况下一天可以被刷 2000 次模型调用。
按当前访客量（约 3 人/天），2000 这个数字没有任何保护作用——它只在被恶意刷量时才生效，
而那时它允许的损失已经足够大。真实需要的量级是几十到几百。

匿名 50/天、注册 300/天 同理，都远高于代码默认值（5 / 30）。
