# 智能生命体的唤醒机制

2026-09-09 · 设计草案。本文描述下一阶段方案，并非已上线能力。

## 产品目标

用户挂一个有价值的问题，数天或数周后回来，能够看清：新增了什么证据、哪些判断改变了、哪些方向失败了、为什么暂停、下一步等什么。系统允许长期休眠，也允许在明确预算内主动获取证据。以可追溯的认知变化衡量进展，不以调用次数、笔记数量或在线时长衡量。

核心闭环：保存等待条件 → 收集线索 → 判断是否值得唤醒 → 执行有限任务 → 核验结果 → 更新判断与阶段 → 再次休眠。

## 现状与缺口

- 项目总览、独立角色配置、经理沟通、逐轮事实记忆、探索分支已存在。
- `services/projectManager.ts` 在经理入口阻止没有新核验事实或背景材料的重复开轮；团队手动入口仍可以重跑。它还不是统一的事件调度规则。
- `services/useInquiryTeams.ts` 管理浏览器内的任务。关闭页面不构成可靠的后台运行。
- `server/explorer-daemon.mjs` 有独立的本地常驻循环，但使用独立项目文件、节点流程和模型配置，尚未接入网页项目的统一团队、事实与唤醒事件；不能直接称为云端长期生命体。
- 当前新团队执行者主要调用文本模型，不具备自动论文采集或现实实验执行能力。没有实际的输入通道，定时思考无法稳定产生外部证据。

## 对用户展示的状态

状态灯表达实际研究活动，不把“模型 API 可以连接”当成在线。云端或本地执行器的可用性另行显示。

| 状态 | 展示 | 用户应该知道什么 |
| --- | --- | --- |
| 睡眠 | 灰灯 | 当前没有值得执行的任务；等待条件、上次进展、下次检查时间 |
| 检查线索 | 绿灯 + 文字 | 正在检查哪些来源；可能很快回到睡眠 |
| 探索中 | 绿灯 + 文字 | 哪个角色在做什么、为什么被唤醒、本次预算和停止条件 |
| 需要你 | 黄灯 | 哪个决定或权限需要用户；不受影响的其他任务可继续 |
| 运行受阻 | 红色提示 | 接口故障、执行器离线、预算耗尽等具体原因及恢复办法 |
| 已暂停 | 灰灯 + 暂停图标 | 用户主动停止；定时器不能自行解除暂停 |

以持久化任务状态与执行器有效心跳显示绿灯，心跳失效转为“连接中断 / 待恢复”，不能永久显示运行。一个想法等待资料，不应阻塞整个项目其他可推进的分支。

## 唤醒事件

1. 用户输入：新问题、目标或约束变化、新材料、显式要求重新思考。先判断意图；闲聊不直接运行全团队。
2. 外部线索：论文更新、数据集版本、用户指定网页变化、实验或计算结果。新线索先进入收件箱，尚不是事实。
3. 认知维护：证据撤回、冲突、过期，或某个结论失去了支持。这些事件通常比扩展新方向更优先。
4. 计划任务：到达预定检查时间、实验预计结束、用户约定的复查日期。
5. 首次激活：即使没有证据，也允许进行一次明确限额的问题澄清、竞争假设和最小验证方案设计。

事件最少保存：eventId、projectId、scopeId、branchId、类型、来源、发生与接收时间、内容指纹、原始材料引用、验证状态、处理状态、影响的假设 ID。恢复探索分支时必须保留事件的分支归属；某分支已经处理过的信息不会在另一分支被静默当成已读。

来源相同而内容未变、同一研究的多篇转载、反复导入同一结果，不应重复调用团队。前两者分别使用内容去重和原始研究关联；无法确定是否同源时保留疑问，不按独立证据累计。

## 两级唤醒

### 第一级：检查

优先使用确定性程序：去重、来源版本检查、是否命中等待条件、用户是否暂停、是否在预算内、是否已有同一任务运行。没有变化时不调用模型。必要时只用一次小型分类任务判断相关性，而不是执行完整研究轮次。

定时器触发“检查”，不直接触发“得出新结论”。这也是区分健康休眠和空转的关键。

### 第二级：有限研究

项目经理根据事件和当前研究状态提出一个小任务单：

- 为什么现在做；影响哪个假设或决定。
- 读取哪些原始材料；已有材料还缺什么。
- 预期产出和可检查的完成标准。
- 最多调用多少次、用多少输出额度、花多长时间。
- 什么条件下停止；结果交给谁核验。

程序检查任务单后，只调用必要角色。例如数据到达先执行与验证；证据冲突优先验证与审计；需要竞争解释再唤醒思想家。避免每个事件固定走 10–19 次调用的完整团队轮次。

新数据不必先经过人工确认才能触发研究，否则用户长期离开后所有任务都会卡住；但它只能触发对材料的核验，不能直接成为已确认的事实。

## 主动性与周期复查

只等待消息会导致问题永远没有进展。因此，每次休眠都应有一份可执行的“等待与采集计划”：待获取什么、从哪里获取、由哪个工具执行、何时检查、命中后影响什么。

首版建议支持：

- 用户手动唤醒随时可用。
- 新线索到达后合并一个短时间窗口内的同类事件，再执行一次检查。
- 默认每天一次检查；连续多次无变化后降低检查频率，重要事件仍可及时处理。
- 每周最多一次有预算的策略复盘，即使没有新外部证据，也可以检查实验设计是否有问题、是否遗漏竞争解释、是否值得更换来源。不得仅靠重述旧材料提高结论置信度。
- 离线错过的多个周期合并为一次，不在恢复后补跑几十轮。

频率、时区和预算均可配置。首版默认值需通过试点调整，不在设计阶段替用户开启付费调用。调用数 / token 上限先做硬限制，金额控制需由服务端使用维护过的价格表核算并预留本次请求额度；不由模型自报成本。

同一假设连续两次没有认知变化，应转入等待，或者提出一个实质不同且成本明确的实验；不能自动换标题继续重跑。预算耗尽、关键工具缺失、无法核验来源或模型连续失败，也应停止并给出原因。

## 事实、判断与失败

区分四层：原始材料 → 候选观察 → 已核验事实 → 基于事实的研究判断。论文的存在不证明其中结论正确；实验返回文件不证明实验设计有效。

低风险、可复现的观测，可在用户预先认可的规则下自动核验，例如对已接入数据做可重算统计，并保留输入、代码版本、输出、范围和验证记录。高影响、存在冲突或无法重现的主张进入待核验。AI 对同一段话的多数赞同不算核验规则。

“失败的实验”需要区分：

- 实验有效且结果不支持假设：属于研究进展，记录排除了什么。
- 代码报错、接口失败或实验设计失效：属于执行问题，不能当成否定假设的证据；记录原因、修复或放弃条件。

稳定保存 hypothesisId、支持与反对的 evidenceId、状态、适用范围、变更原因及未解问题。角色事实记忆继续只继承核验事实；暂定解释和失败经验进入带类型的研究记录，不能混写成可信事实。

## 用户回来后看到什么

项目总览首先呈现“自你上次查看以来”：

- 哪些判断改变了，附前后对比与依据。
- 哪些方向被排除、为什么。
- 哪些有价值的新方向值得验证。
- 哪些事情需要用户决定。
- 现在为什么睡眠，以及下次会因何、何时醒来。

每次有效研究生成一张进展卡：触发原因 → 实际执行 → 结果 → 核验 → 判断变化 → 下一步，关联探索阶段。无变化的检查合并为一条计数记录，保留详细日志入口但不占据摘要。没有新发现时如实说明检查了什么、卡在哪里，不承诺每个月必定有突破。

## 用户离开后运行的基础

需要持久后台：项目状态库、线索收件箱、调度队列、执行器、模型与工具适配、核验与进展存储。网页订阅状态和查看结果，不能充当唯一调度器。

云端托管执行满足关电脑后继续；本地执行器支持用户自己的开源模型，但设备关机时须明确显示离线，不能默默切换到付费云模型。用户现有 API Key 只在浏览器保存，开启后台运行需要单独配置服务端或本地执行器的凭据托管，不能自动上传全部已有密钥。

每项目 / 分支设置执行锁、租约与恢复检查；事件重复投递只能产生一次有效变更。对外部工具使用幂等键、运行 ID 和结果核对，避免超时重试重复执行实验。外部付费调用不应承诺绝对只执行一次，必须处理“已执行但回执丢失”的情况。暂停操作在每个外部调用前检查。任务领取、预算预留、结果提交、事件消费与阶段更新应有一致的提交边界。

所有运行路径统一服从这套策略：网页手动团队、项目经理建议、旧节点循环和后台执行器。手动重新分析是有记录的覆盖指令，不能伪装为新证据。

## 开发分期与验收

第一阶段先交付一个闭环：真实状态灯 + 持久事件队列 + 单一后台执行器 + 用户材料与一种外部采集源 + 有限任务计划 + 进展卡。可优先用论文更新及可复现的本地计算演示，不先承诺任意现实实验自动完成。

第二阶段扩展每天检查、策略复盘、退避、预算与长期恢复；让用户离开数天后仍能看到有依据的更新。第三阶段增加更多工具、数据来源与跨分支复盘。

必须验证：关闭浏览器仍推进；重复事件不重跑；无关论文不唤醒研究；撤回证据能定位受影响判断；无新证据允许有限策略复盘但不空转；用户暂停优先于定时事件；离线补检查不补跑所有周期；预算耗尽停止；本地模型离线不擅自换云模型；执行器重启不重复提交成果；API 超时核对已发生的外部效果；30 天压缩时间模拟中的记录与成本有界。

示例演练（非真实研究结果）：翻译眼镜项目首次醒来设计竞争假设和访谈方案，然后休眠。第三天采集到相关论文，核对后发现样本场景不匹配，仅留下受限启示；第七天访谈结果到达，核验后推翻“日常翻译是主要需求”的原假设，提出特定工作场景方向；后续没有新材料时，检查记录继续累积但不重复写报告。用户月底看到的是这一条有证据、有失败、有方向变化的研究历程。
