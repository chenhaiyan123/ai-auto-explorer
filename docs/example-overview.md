# HiExplore · 总览

> 一句话：HiExplore 是一个「以问题为坐标、以智能为货币」的开源自主探究平台——把有价值的问题挂在后台，让 AI 团队像做工程一样长期研究，需要人拍板时再交回给你。
> 这是一份**填好的范例**，展示一篇好的「项目总览」长什么样。你新建项目时会自动得到一份空模板，照着这个结构填即可。别人只看这一篇，就能了解项目全貌；想深入某点，点 [[链接]] 跳到对应笔记。

## 📌 项目简介

信息爆炸的时代，真正稀缺的不是答案，而是「值得研究的好问题」和「持续把它研究下去的耐心」。人和 AI 的对话大多是一次性的即问即答，问题被回答后就消散了，无法沉淀、无法长大。

HiExplore 想改变这一点：你把一个值得长期投入的问题「立项」，平台像对待一个代码仓库一样对待它——AI 读懂目标、拆成几个关键方向、给每个方向配一个专门的 Agent、在后台持续探索，产出结构化的笔记，并用双向链接织成一张知识图谱。所有数据都存在你自己的浏览器和本地 Markdown 文件里，模型也用你自己的（本地 Ollama 或任意 OpenAI 兼容 API），数据不出本机。

面向两类人：把好奇心变成长期探究的独立研究者 / 创作者 / 开发者；以及需要「挂一个问题、拿到持续可追溯调查」的情报、尽调类工作者。

## 🎯 目标与成功标准

- 核心目标：让一个普通人能像指挥一支研究团队一样，低门槛地对自己在乎的问题做长期、自主、可追溯的探究。
- 怎样算成功：用户愿意把真实的、重要的问题挂上来并持续回看；一个问题在后台跑一周后，产出的笔记确实比一次性问答更深、更有条理。
- 明确不做什么：不做又一个通用聊天机器人；不替用户托管数据或模型（坚持自带模型、本地优先）；不追求一次性给出「标准答案」，而是沉淀过程。

## 🔑 关键点与关键问题

- 关键点一：**问题的组织方式**。把项目做成「文件夹 + README + 总览 + 关键方向子笔记」的仓库结构，是产品体验的地基。 → [[节点笔记化]]
- 关键点二：**模型自由接入**。必须让用户零成本用上自己的本地模型，否则「长期后台探索」的算力成本无人承担。 → [[本地模型接入]]
- 关键点三：**AI 团队协作质量**。多 Agent 分工探索时，要产生合力而不是互相强化错误。
- 关键问题一（尚无定论）：本地小模型 + 长期自主探究，能否在窄领域追平一次性调用的大模型？这决定了产品的核心价值主张是否成立。
- 关键问题二：如何让 AI 自主调用物联网设备做实验，同时保证绝不执行危险或不可逆操作？ → [[IoT设备接入]]

## 🧩 目前遇到的问题

- 问题：`git push` 因 Personal Access Token 缺少 `workflow` 权限被拒。影响：自动部署工作流推不上去。目前思路：在 token 设置里补勾 `workflow` 权限后重推。
- 问题：浏览器从 localhost 访问本地 Ollama 存在 CORS 限制。影响：部分用户首次连本地模型会失败。目前思路：文档里给出 `OLLAMA_ORIGINS="*"` 的解决方案，后续考虑内置检测与引导。
- 风险：本地小模型的探索质量能否达到「可用」尚未系统验证——这是核心价值主张的关键假设，需要尽快用真实项目跑数据检验。

## 💡 关键结论与决策记录

- （2026-06）决定坚持「纯前端 + 自带模型」架构，不自建推理后端。因为这样开源用户零成本、数据不出本机，也让项目可持续（作者不承担算力开销）。
- （2026-06）决定把「问题价值评估 QVS」作为立项前的默认一步。因为长期探索会消耗算力，先判断问题值不值得投入，是这个产品区别于普通问答的核心动作。
- （2026-06）项目更名为 HiExplore，定位从「AI 助手」收敛为「问题驱动的自主探究平台」。
